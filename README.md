# Weather-Aware Truck Routing

Helps a truck driver choose the safest route by combining **forecast weather at the time the truck
will actually be there**, **load weight** and **travel time**.

Enter an origin (or tap **Your location**), destination, departure time and load weight. The app:

1. Generates **3 truck routes** (Valhalla `truck` costing, with the real gross weight).
2. Places checkpoints **every 10 / 25 / 50 miles** and computes the truck's **ETA** at each one.
3. Samples the hourly forecast **at each checkpoint's ETA** and classifies risk with the
   specified wind / rain / snow thresholds and load rules.
4. **Recommends** a route: fewest No-Travel → Severe → High miles → lowest average risk → fastest.
5. Shows routes, risk-coloured checkpoints, ETAs and summaries on a map, plus a **weather heatmap
   over the trip corridor with a 0–48 h forecast slider** (and an animated truck position).

| Layer    | Choice                                                                 |
| -------- | ---------------------------------------------------------------------- |
| Backend  | Django 6 + DRF, stateless (no DB), Redis cache, Gunicorn (gthread)     |
| Frontend | React 19 + TypeScript, Vite, shadcn/ui (Radix) + Skiper UI, TanStack Query, Zustand, MapLibre GL (WebGL), Tailwind v4, Phosphor icons, Geist |
| Data     | Valhalla / OSRM (routing), Open-Meteo (weather), Photon (geocoding), OpenFreeMap (tiles) — all free, no keys required |

## Architecture

```
Browser ──► Django (single origin; WhiteNoise serves the built SPA, /api/* is DRF)
              │
              ├─ POST /api/plan ─► planner.plan()
              │     1. routing.get_routes()      ──► Valhalla truck  (fallback: OSRM)   [cache 6 h]
              │     2. checkpoints + ETAs along each route
              │     3. heatmap.corridor_cells()  (global lat/lon lattice around the routes)
              │     4. weather.fetch_series()    ──► Open-Meteo, batched 50 pts/call,
              │                                      4 calls in parallel              [cache 30 min]
              │     5. risk.assess() per checkpoint → recommend.rank()
              │     6. heatmap.build() 49 hourly frames for the corridor
              ├─ GET /api/geocode ─► Photon (biased toward the trip's other end)      [cache 7 d]
              └─ GET /api/reverse ─► Photon reverse (labels "Your location")          [cache 7 d]
```


## How the logic works

### Routes
* **Valhalla `truck` costing** gets the gross weight = `load + TRUCK_TARE_LB` (35,000 lb default),
  so weight-restricted roads are avoided, and a 65 mph speed governor (`TRUCK_MAX_MPH`) is applied.
* The public Valhalla server rejects requests over 1,500 km straight-line, so longer trips use **OSRM**
  for *all* routes (one provider per trip keeps travel times comparable). OSRM is also the fallback
  if Valhalla is down. The same 65 mph cap is applied to OSRM durations.
* Providers rarely return 3 genuinely different routes. Missing ones are generated by routing through
  **via points offset perpendicular to the trip axis** (18 % and 32 % of the trip length, both sides).
  A candidate is kept only if it is ≤ 1.6× the fastest duration and shares < 80 % of its length with
  every accepted route (grid-hash overlap test). If the via request is too long for Valhalla it is
  routed as two legs and any out-and-back spur at the join is trimmed.

### Checkpoints & ETAs
* Checkpoints at mile 0, every N miles, and the destination. Each checkpoint **represents the stretch
  halfway to its neighbours**, so the per-level miles add up exactly to the route length.
* ETA = departure + the provider's drive time to that point (per-segment times are interpolated
  along the polyline).

### Weather sampling
* Open-Meteo hourly forecast (mph, in/hr, °F). **Wind** is instantaneous → linearly interpolated to
  the ETA. **Rain/snowfall** are “preceding-hour” totals → the hour bucket *containing* the ETA is used.
* Checkpoints beyond the forecast are reported as **No data** and excluded from averages (with a warning).

### Risk rules (exactly as specified)
| Condition | Low | Moderate | High | Severe | No Travel |
| --- | --- | --- | --- | --- | --- |
| Wind (mph) | < 25 | 25–34 | 35–44 | 45–54 | ≥ 55 |
| Rain (in/hr) | < 0.10 | 0.10–0.25 | 0.25–0.50 | 0.50–1.00 | > 1.00 |
| Snow (in/hr) | < 0.5 | 0.5–1.0 | 1.0–2.0 | 2.0–3.0 | > 3.0 |

Load rules: ≥ 55 mph → No Travel for any load · 45–54 mph with > 30,000 lb → No Travel ·
35–44 mph with > 40,000 lb → Severe. A checkpoint's level is the **worst** of wind (after load rules),
rain and snow.

Boundary interpretation: bands include their lower bound (34.6 mph is Moderate, 35.0 is High; 0.25 in/hr
rain is High). The top bands for rain/snow are strict as written (exactly 1.00 in/hr rain is Severe).
“Wind” is the sustained 10 m wind speed; gusts are shown for context. All boundaries are unit-tested.

### Recommendation
Lexicographic ranking: **No-Travel miles → Severe miles → High miles → average risk → travel time**.
No-Travel is ranked first because a route through No-Travel conditions must never beat a merely Severe
one. Small tolerances (1 mile, 0.05 average-risk points) stop negligible risk differences — e.g. half a
Severe mile — from outweighing hours of driving; that is how risk is balanced against time. Each
recommendation explains the deciding criterion against every other route.

### Heatmap & slider
* The corridor is the set of cells of a **global** lat/lon lattice within a buffer of any route.
  The finest lattice step that fits `HEATMAP_MAX_CELLS` is chosen; global snapping lets different trips
  share cached cells.
* The API returns 49 hourly frames (risk, wind, rain, snow) per cell. The frontend uploads them to the GPU
  **once** as feature properties (`r0…r48`, `w0…`). Moving the slider only swaps the layer's
  `heatmap-weight` expression via a direct Zustand subscription, so **no React render, no data upload and
  no re-tiling** happen per frame.
* Kernel radius/intensity are derived from the lattice spacing so the field's density equals the cell
  value at every zoom level.

## User experience

A dark **fleet-console** layout (inspired by the *Logistat* fleet-tracking concept on Dribbble), built
entirely from **shadcn/ui** components (Radix primitives, CSS-variable theme) with **Skiper UI**
components for the motion details, Phosphor icons and the Geist / Geist Mono typefaces.

**Desktop** (`lg` and up): trip and routes on the left, the map on the right.

* **Trip card**: pick-up / drop-off autocomplete (shadcn *Command* in a *Popover*) with
  **“Your location”** (browser geolocation plus reverse geocoding), swap, a departure **calendar** (shadcn *Calendar*,
  today to +5 days, with a 15-minute time field) that offers **“Leave now”** first, load weight, and the
  10 / 25 / 50 mi weather-check interval (*Tabs*). Plans update automatically.
* **Route list**: every option uses the same card: route name with *Safest* / *Fastest* badges,
  “via I-70 and US-6”, distance, driving time, checkpoints, miles at High risk or worse, and a **Safety %**
  ring (`100 × (1 − average risk ÷ 4)`). The recommended route is the blue card; the selected one is outlined.
* **Map**: a dark basemap, the selected route painted as a smooth gradient on **one colour scale for every
  layer** (green = OK → yellow → orange → red = not OK, at the brief's thresholds), grey alternatives with duration
  callouts, A/B pins and a truck marker. Overlays:
  * a blue route-stats pill;
  * the on-map layer bar (Risk / Wind / Rain / Snow, plus hiding the heatmap);
  * the **trip timeline**: one bar that is both the trip and the forecast scrubber (*Slider*, 15-minute steps).
    By default it spans exactly the journey (departure → arrival, with adaptive hour ticks); the **48h** toggle
    widens it to the full 0–48 h forecast horizon for the heatmap. Colours show conditions at the time the truck
    passes each point, and the navigation-arrow knob is dragged to scrub or clicked to play/pause;
  * a **conditions card** showing the forecast at the truck's position.
* **Weather report** (*Sheet*): why the recommended route wins, plus the forecast stretch by stretch.

**Phones** (below `lg`): a stacked layout where finished steps fold away and details open on selection.

* the trip form **wraps into a one-line summary** once routes arrive (“Denver → Salt Lake City · Leave now ·
  40,000 lb”); tap it to edit;
* the map fills the screen, with a single **Layers** menu (*Popover*) and a compact timeline whose readout
  shows the conditions at the truck; zoom buttons are dropped in favour of pinch-zoom;
* the routes sit in a **bottom bar** with a one-line summary of the selected route and a report button. Tapping
  it raises an **accordion** route list over the map (so the map never resizes): the selected route is the full
  card, the others are slim rows. Picking a route, or tapping outside, folds it away;
* the weather report slides up from the bottom.

**Skiper UI** components used (free tier, attribution required): Custom tooltip (skiper101),
Animated number (skiper37) and Progressive blur (skiper41), by
[@gurvinder-singh02](https://skiper-ui.com). Runtime `<style>` tags from Radix ScrollArea and NumberFlow
are allowed in the CSP by exact SHA-256 hash, not `'unsafe-inline'`.

## Production concerns

* **Performance:** batched + parallel upstream calls; Redis caching of routes, weather and geocoding;
  route geometry simplified (Douglas–Peucker, 25 m) and polyline-encoded; gzip; MapLibre lazily
  loaded in its own chunk; hashed assets served `immutable`; `content-visibility` for long lists; overlays and animation code are lazy-loaded after the first plan.
  Cold plan ≈ 2–5 s (mostly upstream APIs); repeated / interval change ≈ 50 ms.
* **Resilience:** connection pooling, retries with backoff, `Retry-After` capped at 5 s,
  provider fallback, partial-weather tolerance, uniform JSON errors (400/422/429/502/503).
  Optional alternative-route probes fail fast (8 s, no retries) so a slow public router can't stall a plan.
* **Security:** strict CSP (no inline scripts or styles), HSTS, SSL redirect, nosniff, `X-Frame-Options:
  DENY`, COOP, referrer policy; strict input validation (DRF serializers + zod); per-IP throttling
  (`THROTTLE_PLAN`, `THROTTLE_GEOCODE`); small request-body limit; non-root container; no secrets in the client.
* **State:** TanStack Query owns server state (dedupe, cancellation, caching per trip+interval);
  Zustand owns UI state. Redux would add boilerplate without benefit at this size.

## API

`POST /api/plan`
```json
{
  "origin": {"lat": 39.7392, "lon": -104.9903},
  "destination": {"lat": 40.7608, "lon": -111.891},
  "departure": "2026-11-10T14:00:00Z",
  "load_lb": 42000,
  "interval_mi": 25
}
```
Returns `routes[]` (geometry, distance, duration, arrival, `stats.miles_by_level`, `checkpoints[]` with ETA,
weather, level and drivers), `recommendation` (`route_id`, `comparisons[]`), `warnings[]` and `heatmap`.
Each route also carries `via` (main roads, e.g. `"I-70 and US-6"`).
`GET /api/geocode?q=denver[&lat=&lon=]` → `{results: [{label, lat, lon}]}` ·
`GET /api/reverse?lat=&lon=` → `{label}` · `GET /api/health`.

## Deployment

One Docker image (multi-stage: Node builds the SPA, Python serves API + SPA).

* **Vercel (hosted demo, free Hobby plan):** import the GitHub repo and set `DJANGO_SECRET_KEY`.
  `vercel.json` builds the SPA to Vercel's CDN (same security headers / CSP as Django sends) and runs the
  Django API as one Python function (`api/index.py`); Vercel hostnames are allowed automatically.
  Without Redis the cache is per function instance, which is fine for a demo.
* **Hugging Face Spaces:** a *Docker* Space with `app_port: 8000` in the Space's
  README header, and `DJANGO_SECRET_KEY` as a Space secret. The Space hostname (`SPACE_HOST`) is allowed
  automatically, and only on a Space is `huggingface.co` permitted to frame the app.
* **Render:** *New → Blueprint* with `render.yaml` (web service + Redis-compatible cache), or a single
  Docker web service with `DJANGO_SECRET_KEY` set. `RENDER_EXTERNAL_HOSTNAME` is allowed automatically.
* **Any Docker host:** set `DJANGO_SECRET_KEY`, `DJANGO_ALLOWED_HOSTS`, optionally `REDIS_URL`
  (see `.env.example`). Without Redis the app falls back to an in-process cache.

## Assumptions & limitations

* Free public providers have usage limits. Open-Meteo's free tier allows ~600 locations/minute
  (a plan uses ~150–450); set `OPEN_METEO_API_KEY` for production volume. Self-hosted Valhalla removes
  the 1,500 km limit (`VALHALLA_URL`, `VALHALLA_MAX_MI`).
* ETAs are continuous driving (no Hours-of-Service breaks or live traffic).
* “Your location” needs HTTPS (or localhost) and the user's permission, as with any website.
* Departure must be within the next 5 days so the trip and the 48 h heatmap fit the 7-day forecast.
